# 任务规划、上下文与线上评估

FinCredit Copilot v0.9 将 Agent 的执行升级为可审计的受控任务规划、上下文治理、人类反馈与 Prompt 发布闭环。设计原则是：**模型负责受约束的表达，不负责选择高风险动作；确定性系统负责计划、工具权限、数据最小化、上下文预算、评估、Prompt 变更与人工审批边界。**

## 受控任务规划

`app/task_planner.py` 只支持两个业务任务：`generate_brief` 和 `answer_question`。每次规划生成稳定的版本 ID、目标、问题分类和依赖步骤：

```text
申请/问题
  -> 申请快照 ─┐
  -> 中台规范客户快照 ─┼-> 上下文质量检查 -> 确定性风控规则 -> RAG 政策证据
  -> 材料状态 ────────┘                         -> schema 结构化输出
  -> 审批状态（仅流程问题）                                         -> 人工审批边界
```

- 工具只能来自白名单，规划器不接受模型生成的工具名。
- 所有工具均为只读；“人工审批边界”是必经治理步骤，不存在“批准授信”工具。
- 每个步骤、实际工具轨迹和完成状态保存到 Agent Run 输入快照，失败 Run 重试时重新生成同版本计划。
- 计划是确定性的金融业务编排，不是开放式自治 Agent；若增加新工具，必须同步进行权限、脱敏、审计、回归测试和发布评审。

## 数据中台最小化上下文

`get_canonical_customer_snapshot` 从数据中台读取申请所属组织的当前 `customer` 记录，并执行两层边界：

1. 只返回行业、经营年限、营收、负债率、逾期天数、信用等级、记录哈希和入库时间；标识字段、原始材料及载荷不进入模型上下文。
2. 分级为 `restricted` 的记录返回拒绝原因，不返回字段内容；没有规范记录时明确返回不可用，不虚构数据。

模型调用前，`app/context_governance.py` 创建证据和工具结果的独立副本，并以 `FINCREDIT_AGENT_CONTEXT_MAX_CHARS` 执行硬字符预算。超额证据正文会被截断，但每个证据 ID、标题和引用元数据仍保留；完整正文仍只保存在报告证据链，不因模型预算而丢失。运行快照写入预算、实际字符数、截断证据 ID、上下文哈希，以及中台数据的 `fresh/stale/unknown` 时效与跨源字段冲突名称。`FINCREDIT_CANONICAL_DATA_MAX_AGE_HOURS` 默认为 `168`；时效或冲突是人工复核提示，不会改写确定性规则的权威输入。

该上下文是辅助信息，不会覆盖受控业务库中用于确定性规则和审批的一手数据。生产切换权威数据源前，应完成来源责任、数据质量、时效、主数据匹配、字段级授权与业务签字。

## 线上评估与漂移告警

线上评估使用已持久化的完成 Run，不采集新的客户信息。窗口大小由 `FINCREDIT_ONLINE_EVALUATION_WINDOW_RUNS` 控制，样本量未达到 `FINCREDIT_DRIFT_MIN_SAMPLES` 时状态为 `insufficient_data`；尚未建立基线时状态为 `baseline_required`，两种状态均不能宣称模型健康。

| 信号 | 数据来源 | 告警条件 |
| --- | --- | --- |
| 降级率 | `output.fallback` | 高于基线 + 5 个百分点或硬阈值 |
| P95 延迟 | `input_snapshot.duration_ms` | 高于基线 1.5 倍 + 50ms 或硬阈值 |
| 证据覆盖 | 输出证据 ID / 检索证据 ID | 低于基线 5 个百分点或最低阈值 |
| 规划一致性 | 计划工具、实际工具、步骤状态 | 低于基线 5 个百分点或最低阈值 |
| 决策边界 | 结构化输出的禁止自动决策短语 | 任意命中立即告警 |

线上窗口还汇总已完成 Run 的 `feedback_count`、`feedback_coverage`、`human_acceptance_rate` 与 `human_correction_rate`。反馈目前是可观察质量信号，不会自动修改模型、规则或授信结论，也不以反馈率直接触发漂移告警。

建立基线应在经合规批准、真实但脱敏的稳定观察期后进行。告警会持久化为 `open`；随后评估恢复正常时会标记 `resolved`，保留首次和最近发现时间。生产需要将这些事件连接到企业告警和值班流程，而不是依赖人工定期刷新页面。

## 人工反馈与告警处置

风险经理、审批人或合规管理员可对一个已完成的 Agent Run 提交一次反馈，结论为 `accepted`、`needs_revision` 或 `incorrect`，并选择事实、证据、风险判断、表达或其他类别。反馈文本长度受 API 限制，保存提交人、时间和内容哈希；它不复制材料正文或模型提示词。重复提交会返回 `409`，避免覆盖既有复核记录。

合规管理员可为任意已存在漂移告警追加 `acknowledged`、`investigating` 或 `false_positive` 处置记录。记录是追加式的，不会关闭或删除原告警；告警仅在后续评估中信号恢复时自动标记 `resolved`。

| API | 作用 |
| --- | --- |
| `GET/POST /v1/applications/{application_id}/agent-runs/{run_id}/feedback` | 查询或提交完成 Run 的结构化人工复核 |
| `GET /v1/observability/drift-alerts/{alert_id}/actions` | 查询告警处置历史 |
| `POST /v1/observability/drift-alerts/{alert_id}/actions` | 追加合规处置记录 |

## 反馈驱动的 Prompt 发布

`prompt_versions` 将两个 Agent 任务的内置 v1 Prompt 保存为活动基线。合规管理员只能创建新版本草稿；草稿可关联已经存在的人工反馈编号，并保存变更原因与内容 SHA-256。提交后，作者和提交人均不能审批。独立合规管理员审批时会再次验证内容哈希，并检查 Prompt 仍保留“不得自动批准、拒绝或退回授信申请”、合法 JSON 及任务必填输出字段等不可删除约束。

批准会在一个事务中退役同任务的旧活动版本并激活候选版本；被拒绝版本不参与运行时选择。每个 Run 在构建上下文时固定 Prompt 内容、ID 和版本，因此激活发生在执行期间也不会影响已开始运行的模型调用。回滚不会直接重启旧版本，而是从已批准版本复制为新的草稿，重新走四眼审批。

`FINCREDIT_PROMPT_VERSION` 仅可用于核验部署时当前活动版本是否与期望版本一致；它不能选择已退役版本或覆盖 Prompt 内容，失配会失败而非静默降级。

## 按六项标准的持续优化路线

| 阶段 | 对应标准 | 已完成的基线 | 下一项可验收工作 |
| --- | --- | --- | --- |
| A | 真实问题 | 预审、材料、规则、政策、人工审批闭环 | 接入经授权的 CRM/核心信贷/征信脱敏回放，定义业务成功指标与人工采纳率 |
| B | 后端工程 | 分层 API、迁移、事务、OIDC、pgvector、数据契约 | PostgreSQL + Alembic、对象存储、幂等接入、限流、CDC、灾备演练 |
| C | 任务规划 | 版本化受控依赖图、工具白名单、Run 可恢复、上下文质量步骤 | 有审批的计划版本发布、步骤 SLA、人工暂停/恢复队列和跨任务编排 |
| D | 上下文处理 | RAG 证据、脱敏工具、规范数据最小化读取、字符预算、时效/冲突检测 | 会话摘要、权限感知检索、已批准的长期记忆 |
| E | 评估监控 | 离线门禁、线上指标、基线、漂移告警、反馈覆盖/修订率 | 标注集、业务结果/偏差监控、灰度实验、Prometheus/SIEM 告警 |
| F | 人机协同 | 四眼规则、人工审批、覆盖理由、结构化 Run 反馈、告警处置历史、反馈关联 Prompt 四眼发布和回滚 | 变更工单联动、发布后效果复盘、可控灰度和回滚演练 |

每个阶段都应先定义数据分级、验收样本、量化阈值、回滚方式和责任人。真实生产数据、授信政策和模型配置的变更必须经过业务、风险、合规和安全联合审批。
